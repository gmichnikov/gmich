01 — Overview

What we're building

SS to Cal is a personal Android PWA that registers in the system share sheet. Take a screenshot of anything with event info — an email, a WhatsApp message, an Instagram post, a flyer — share it to SS to Cal, verify the extracted details, and add it to Google Calendar. No typing. No switching apps. No missed events.

SS to Cal is one project (ss_to_cal) within a larger Flask web app (the hub), already live on Heroku over HTTPS. It is registered in the hub project registry at /ss-to-cal. A vision-model API call happens server-side — API keys are never exposed to the browser. Android shares an image via the Web Share Target API; Flask receives the multipart POST, extracts event details, and returns a review form page.

02 — Problem

The friction we're eliminating

Events arrive everywhere — a WhatsApp message, a restaurant confirmation email, an Instagram story, a Meetup screenshot. Getting them into a calendar today means reading the screenshot and manually typing title, date, time, and location into a calendar app, usually while switching between apps and losing context. Things get missed.

The goal is to reduce the entire flow to: screenshot → share → verify → done, using the Android share sheet pattern users already know.

03 — User flow

Step by step

1
Take a screenshot

Screenshot anything containing event info — an email, chat message, social post, flyer, or web page.

2
Share to SS to Cal

Tap Share. SS to Cal appears in the Android share sheet (after the PWA is installed to the home screen). Tapping it POSTs the image directly to /ss-to-cal/share — no copying, no manual uploading.

3
AI extracts what it can find

Flask receives the image from the share POST, resizes it server-side, and sends it to a vision model with a structured extraction prompt. The model returns a JSON object with whatever it can confidently identify. Fields it cannot determine are returned as null — it never guesses or invents values. This takes 2–4 seconds on LTE.

4
Review & complete

A form opens pre-filled with everything the model found. Missing or uncertain fields are highlighted in amber and labelled "Required" or "Please verify." The user fills in any gaps. The "Add to Google Calendar" button is disabled until title and date are both present. Timezone defaults to the device's local timezone and can be changed.

5
Add to Google Calendar

One button opens Google Calendar in the browser with all fields pre-populated. The user taps Save. Done.

04 — Missing fields behavior

When the screenshot is incomplete

This is a core design principle: SS to Cal never assumes. It always asks. If information isn't clearly present in the screenshot, the user must supply it — the app does not fill in defaults silently or make educated guesses about dates and times.

The model is instructed explicitly: if you are not confident about a value, return null. Never infer. Never guess. A null field is always better than a wrong field.

Field-by-field behavior

Field Required? If missing or null
Title Yes Field highlighted amber, labelled "Required." Add to Calendar button stays disabled until filled.
Date Yes Field highlighted amber, labelled "Required." Add to Calendar button stays disabled until filled.
Start time No Field is empty with a "Leave blank for all-day event" hint. User can enter a time or leave it blank — blank means all-day.
End time No Empty, optional. If a start time is set but no end time, Google Calendar will default to a 1-hour event.
Location No Empty, optional. No prompt shown.
Description No Empty, optional. No prompt shown.
Timezone No Defaults to device's local timezone. Always visible. If the model detected a different timezone, it is pre-filled and highlighted amber with "Please verify."

The review form always opens — even if every field is null. The user is never shown a "couldn't find anything" dead end. They simply fill in what's missing.

Confidence indicator

The model also returns an overall confidence value (high, medium, or low). When confidence is low, a banner is shown at the top of the review form: "The image was hard to read — please check all fields carefully." Individual fields with medium or low confidence are marked "Please verify" regardless of whether they are null.

05 — Requirements

What the app must do

Functional requirements

FR-01

Register as a share target in the Android share sheet, accepting image/* files via the Web Share Target API.

FR-02

Send the received image to a vision-capable LLM and parse a structured JSON event object from the response. Never display raw API output to the user.

FR-03

Always open the review form after extraction, regardless of how many fields were found. Never show a dead-end error screen for incomplete extractions.

FR-04

Highlight null and low-confidence fields in amber. Required fields (title, date) show a "Required" label. Others show "Please verify." All fields must be editable.

FR-05

Disable the "Add to Google Calendar" button until both title and date are filled in. Enable it immediately once both are present.

FR-06

Generate a valid Google Calendar URL from the confirmed event data and open it in the browser. Support all-day events (no time) and timed events.

FR-07

Show a timezone field on every review form. Default to the device's local timezone. User can change it before submitting.

FR-08 — Authentication

Access to SS to Cal routes is gated by the hub's existing authentication (Google OAuth / Flask-Login). No separate signup or onboarding. The PWA shell and share route require a logged-in session. Manifest and service worker are served without auth.

Non-functional requirements

NFR-01 — Speed

Extraction result appears within 5 seconds on LTE. On share-target POST, Android sends the full image — Flask resizes/compresses server-side (max 1600px longest edge) before calling the vision model. No database; screenshots are not stored after extraction.

NFR-02 — Privacy

Screenshots are sent to the Flask backend and then to the vision API. They are not stored after extraction completes. API keys live server-side as Heroku environment variables and are never exposed to the client.

NFR-03 — Offline

App shell (HTML, CSS, JS) loads offline via service worker. Extraction requires connectivity. A clear error is shown when offline.

NFR-04 — Installability

Meets PWA installability criteria in Android Chrome. Runs as a standalone app (no browser chrome) when launched from the home screen.

06 — Error states

What happens when things go wrong

All errors are shown inline in the UI — never as browser alert() dialogs. Every error state includes a clear message and a recoverable action (retry, go back, or open settings).

Condition Message shown Recovery action
OFFLINE "You're offline. Connect to the internet and try again." User must re-share the screenshot once online. (Share-target POST cannot be retried with the same image held in memory.)
NOT_LOGGED_IN "Please log in, then share the screenshot again." Show a dedicated page (HTTP 200) — do not redirect to login, which would drop the multipart POST body. User logs in via the hub, then re-shares from the gallery.
API_ERROR "Couldn't reach the extraction service. Try again." Retry button.
PARSE_FAILED "The AI returned an unexpected response. Try again." Retry button. The raw response is logged to console for debugging.
NO_EVENT_FOUND "No event details were found in this image. You can fill in the details manually." Opens the review form with all fields empty. User fills everything in manually.
IMAGE_TOO_LARGE "The image couldn't be processed. Try a clearer screenshot." Go back button. Happens if server-side resize/decode fails unexpectedly.
07 — Technical spec

How it's built

Hub project
Blueprint ss_to_cal at /ss-to-cal. Listed in app/projects/registry.py with auth_required: true. Static assets under /ss-to-cal/static/. CSS classes prefixed sstc- to avoid collisions with other hub projects.
Type
One blueprint/project within the existing Flask hub. Front-end is a PWA with a web manifest and service worker served by Flask. No database models in v1.
Hosting
Existing Heroku deployment, already on HTTPS. No new infrastructure needed.
AI model (v1)
gemini-3-flash-preview via Google Gemini API (google.genai client). Same pattern as sports_schedules and docs_demo.
Fallback model
claude-sonnet-4-6 via Anthropic Messages API — switch only if Gemini misses the section-08 accuracy bar (see Model selection below).
API keys
Primary: GOOGLE_API_KEY (already used elsewhere in the hub). Fallback: ANTHROPIC_API_KEY. Never sent to the client.
Share target
manifest.webmanifest declares share_target with method: POST, enctype: multipart/form-data, accepting image/*. Android POSTs to /ss-to-cal/share. PWA scope is /ss-to-cal/ so the installed app stays within this project.
Share handoff
The share POST goes directly to Flask — no Cache API relay, no separate JSON API in v1. Flask reads the image, calls the vision model server-side, and returns an HTML review form with extracted fields embedded (e.g. as JSON in the page). The user edits and opens Google Calendar via a client-built URL.
Image encoding
Android sends the full image in the share POST. Flask resizes to max 1600px on the longest edge, then sends to the vision API. Screenshots are not persisted after extraction completes.
Authentication
GET /ss-to-cal/ and POST /ss-to-cal/share require a logged-in hub session. /ss-to-cal/share is CSRF-exempt (Android share POST has no CSRF token). Unauthenticated share POSTs return a login prompt page (200), not a redirect. User must log in during PWA install and keep an active session when sharing.
Framework
Flask (Python) back-end. Vanilla HTML/CSS/JS front-end. No JS framework or build step.

Model selection

Default to Gemini 3 Flash for v1. It is already used in this hub, fast enough for the <5s target, and cheap at personal-use volume (~$0.003/call). Switch to Claude Sonnet 4.6 only if manual testing on section-08 screenshot types fails the success criteria — especially invented dates/times or missed title+date on WhatsApp or flyer screenshots.

Role Model ID When to use
Default (v1) gemini-3-flash-preview Ship with this. Reuse google.genai.Client + GOOGLE_API_KEY from existing hub projects.
Quality fallback claude-sonnet-4-6 If Gemini invents dates, misses casual phrasing (“next Friday”), or falls below 8/10 on section-08 fixtures. Uses ANTHROPIC_API_KEY.
Budget fallback gemini-2.5-flash-lite Only if cost ever matters at scale; not expected for personal use.

Model choice is validated empirically on real screenshots (section 08), not benchmark tables. Prompt quality and server-side resize matter as much as the model.

Extraction system prompt (verbatim)

Sent as the system message on every extraction API call
You are an event extraction assistant. Your job is to extract
calendar event details from screenshots.

Rules you must follow without exception:
- Respond ONLY with a single valid JSON object. No explanation,
  no preamble, no markdown, no code fences.
- If you are not confident about a value, return null for that field.
- NEVER guess, infer, or fabricate dates, times, or locations.
- A null field is always preferable to a wrong field.
- If the image contains no identifiable event, return:
  {"error": "no_event_found"}
- Dates must be ISO 8601: YYYY-MM-DD
- Times must be 24-hour HH:MM format
- Timezone must be an IANA timezone name, e.g. "America/New_York"

Extraction JSON schema

Shape the model returns on success
{
  "title":       "string" | null,   // Event name
  "date":        "YYYY-MM-DD" | null,
  "startTime":   "HH:MM" | null,    // null = user chooses all-day or enters time
  "endTime":     "HH:MM" | null,
  "location":    "string" | null,
  "description": "string" | null,
  "timezone":    "string" | null,    // IANA name, e.g. "America/New_York"
  "confidence":  "high" | "medium" | "low"
}

Required fields are title and date. All others are optional. The review form surfaces any null or uncertain field to the user before the calendar button is enabled.

08 — Screenshot types

What the app needs to handle

The model should be tested against each of these categories. Difficulty is based on how structured and text-rich the content is — dense text with clear labels is easiest; image-heavy content with informal date phrasing is hardest.

Source type Difficulty Notes
Confirmation email Easy Structured text, explicit date/time fields, usually unambiguous.
Calendar invite (email) Easy Highly structured. Title, time, location usually labeled.
WhatsApp / iMessage Medium Casual date language ("next Friday", "this weekend"). Timezone rarely mentioned.
Eventbrite / Meetup page Easy Structured event pages with clear fields. Strong signal.
Instagram / Facebook event Medium Date formatting varies. Location sometimes missing or informal.
Event flyer (image-heavy) Hard Dates embedded in graphics, creative typography, no semantic structure. Model may return low confidence.
Restaurant / venue website Medium Usually has address and hours but event-specific info may be sparse.
Screenshot of a ticket (PDF/image) Medium Structured but compressed layout. Barcodes and noise may affect model focus.

For "hard" screenshot types, the model is expected to return confidence: "low" and null for uncertain fields rather than guessing. The user fills in what's missing.

09 — Calendar integration

Google Calendar — no API required

SS to Cal opens Google Calendar's new event form via a URL redirect, with all confirmed fields pre-populated. No Google OAuth or Calendar API credentials needed. The user sees a pre-filled form in Google Calendar and taps Save.

URL structure

Constructed client-side from the verified form data
https://calendar.google.com/calendar/render
  ?action=TEMPLATE
  &text=Event+Title
  &dates=20260601T140000Z/20260601T150000Z
  &details=Description+here
  &location=123+Main+St

All values are URL-encoded from the verified form fields. Times are converted to UTC before encoding using the timezone the user confirmed. All-day events (no time set) use the date-only format: YYYYMMDD/YYYYMMDD with the end date set to the day after the start date (as Google Calendar requires).

V1 is Google Calendar only. Other calendar targets (Outlook, .ics) are out of scope.

10 — Install flow

Getting SS to Cal into the share sheet

The share sheet registration only works once the PWA is installed to the home screen. This is a one-time setup. The app should surface these instructions on first load if it detects it is running in a browser tab rather than as a standalone PWA.

1

Open /ss-to-cal/ in Chrome on Android. (Other Android browsers may not support the Web Share Target API.)

2

Log in with the hub's Google OAuth if prompted.

3

Tap the three-dot menu in Chrome's top-right corner.

4

Tap "Add to Home Screen" and confirm. SS to Cal installs as a standalone app.

5

Test the share sheet: take any screenshot, tap Share, and confirm SS to Cal appears in the list. If it doesn't appear, try restarting Chrome.

The app detects whether it is running as an installed PWA (display-mode: standalone) or in a browser tab. In a browser tab, it shows the install instructions above instead of the normal UI, since share sheet integration won't work.

11 — Success criteria

How we know it's working

V1 is considered done when all of the following hold in manual testing across the screenshot types listed in section 08.

8/10

Correctly extracts title and date from 8 out of 10 representative screenshots without user correction.

<5s

Extraction result — whether successful or an error state — appears within 5 seconds on LTE.

0

Zero instances of the model inventing a date or time that wasn't present in the screenshot.

Functional

The share sheet integration works: sharing a screenshot to SS to Cal opens the review form with extracted data.

Functional

The Google Calendar URL correctly pre-fills all confirmed fields including timezone conversion.

Functional

Every error state (no key, offline, API failure, no event found) shows a clear message with a recovery action.

UX

The "Add to Calendar" button never enables with an empty title or date. Amber highlights correctly identify all null fields.

12 — Scope & non-goals

What's in and what's out

Uses the hub's existing login — not a separate user system. No email, no event history, no database in v1.
