01 Overview & Design Philosophy

This is a real-time collaborative bowling scorekeeper. A group of people bowling together can share a 6-digit code and all score the game from their own phones simultaneously. There are no user accounts, no login, and no memory of players between games.

Core Principles

  • Mobile-first, always. This app will be used almost exclusively on phones, in bowling alleys. Every interaction must be thumb-friendly, readable in dim lighting, and fast to use with one hand.
  • Simplicity over features. No animations, no dark/light mode toggle, no handicaps, no player profiles, no history across games.
  • Flexible scoring. There is no enforced turn order for entry — any scorer can enter a roll for any player at any time. The app shows whose turn it logically is, but does not block other entry.
  • Small user base. Design for reliability and simplicity, not scale. Polling-based sync is fine.

Navigation Note
When someone opens the app with a 6-digit code (e.g. via a shared link or manual entry), they land directly on the correct screen for that game's current state: Setup if not yet started, Active if in progress, Completed if finished.

Joining a Game

From the Home screen, a user enters the 6-digit code and taps Join. If the code is valid, they land on the current state of that game. If the code is invalid or not found, show a clear inline error: "No game found with that code."

Setup Screen — Joining Late

If a second person joins a game that is still on the Setup screen (not yet started), they see the same Setup screen as the creator. Both can add/reorder players. There is no concept of "host" — all scorers are equal.

03 Game Setup

Creating a Game

When the creator taps "Create New Game," the server immediately generates a unique 6-digit numeric code (e.g. 482031) and creates a game record. The creator is taken to the Setup screen, where the code is shown prominently so it can be shared with other scorers.

Code Generation
Codes are 6-digit zero-padded integers (000000–999999), chosen randomly from codes not currently in use. Since games persist forever, "not in use" means no existing game record has that code. With a small user base this space is effectively unlimited.

Adding Players

  • Players are defined by a single name string only. No avatars, IDs, or other metadata.
  • Any number of players can be added.
  • Players can be reordered via drag-and-drop (or up/down tap buttons — whichever is more reliable on mobile). Order matters: it determines turn sequence and the "whose turn" logic.
  • Player names are not remembered across games.
  • Player names cannot be edited once the game has started. All name changes must happen on the Setup screen before "Start Game" is tapped.
  • The Start Game button should only be enabled once at least one player has been added.

Sharing the Code from Setup

The game code is generated the moment a game is created — before any players are added. The Setup screen should display it prominently with a one-tap copy button, since this is the natural moment to share it: "Here's our game code, join before we start." The code remains visible and copyable on the Active Game screen as well, for anyone who joins late.

Late Player Addition Lock

Once the game has started, players can still be added from the Active Game screen — until any player has rolled their first ball of Frame 2. At that point, the player list is locked and the "Add Player" option is hidden/disabled.

A player added after the game has started simply has blank/zero scores for any frames already played by other players. They begin play with Frame 1 regardless of where others are in the game.

Important Edge Case
The lock condition is: any player's second frame has at least one roll entered. Not "frame 2 is complete," just that the first roll of frame 2 has been recorded for anyone. This prevents adding players who would have a meaningful scoring disadvantage.

Standard Scoring Rules

StrikeAll 10 on first roll

Display X in the single roll box. Score = 10 + next 2 rolls. Frame score shown as pending until bonus rolls are recorded. Only one roll box used for frames 1–9.

SpareAll 10 across both rolls

Display / in the second roll box. Score = 10 + next 1 roll. Frame score shown as pending until the bonus roll is recorded.

Open FrameFewer than 10 pins

Score = sum of the two rolls. No bonus. Score is shown immediately after the second roll.

GutterZero pins

Display – (dash) instead of 0 in the roll box, following standard scorecard convention. The pin input button is labeled 0 but the scorecard renders it as –.

Frame 10 Special Rules

The 10th frame always displays 3 roll boxes. The rules for how many rolls a player actually gets:

  • Strike on first roll: Player gets 2 more rolls (3 total).
  • Spare after first two rolls: Player gets 1 more roll (3 total).
  • Open (no strike or spare): Player only gets 2 rolls. Third box stays blank/locked.
Frame 10 Scoring Detail
The frame 10 score is simply the sum of all rolls taken (2 or 3). There is no additional bonus beyond the extra roll(s) earned. Running total = sum of frames 1–10.

Pending Scores

Because rolls can be entered out of order across players, a frame's score may be "pending" — the bonus rolls needed to calculate it haven't been entered yet. Display a visual indicator (e.g. … or a dash) in the frame score area when a score cannot yet be computed. The running cumulative totals for all subsequent frames should also be left blank/pending in this case.

Cumulative Score

The rightmost column shows each player's total score — the sum of all completed (non-pending) frames. If any frame is pending, the total should only reflect frames up to and including the last non-pending one.

How Input is Triggered

The pin input panel should make clear which player and which roll is being entered. The suggested UX: tapping a player's current frame on the scorecard opens the input panel with a clear label like "Alice — Frame 5, Roll 1."

Since entry is not enforced in order, scorers can also tap any player's in-progress frame to enter a roll for them. The input panel validates based on the specific roll context of that player.

06 Turn Indicator

The app displays a subtle indicator of whose turn it logically is. This is advisory — it does not block entry for other players.

Algorithm

The "current player" is determined as follows:

  1. Count the number of completed frames for each player. A frame is complete when all its rolls have been entered (and it is not awaiting input for more rolls in that frame).
  2. The current player is the one with the fewest completed frames.
  3. If multiple players are tied on completed frames, the one with the lowest position in the player order wins the tiebreak.
  4. Because player positions are always unique, there is always exactly one current player.

Display

The current player's row on the scorecard is marked with a small colored indicator — for example, a left border accent or a small arrow/chevron before their name (as shown in the scorecard example above). No banner or modal — just a subtle row highlight.

Example
Player order: Alice (1), Bob (2), Carol (3). Alice has completed 4 frames, Bob 5 frames, Carol 4 frames. Fewest is 4 (tied: Alice and Carol). Alice is earlier in order → Alice is shown as current.

07 Score Correction (Clear Frame)

There is no undo button. Instead, scorers can clear a player's current or most recently completed frame and re-enter it. Think of each player's frame history as a stack — only the top of the stack can be cleared.

The Rule

  • For each player, only their highest-numbered frame with any rolls entered can be cleared.
  • Clearing a frame removes all rolls recorded for that frame and resets it to blank.
  • After clearing, the next-highest frame becomes clearable.
  • This allows a scorer to "unwind" as many frames as needed, one at a time.

Example Walkthrough

Alice has rolls entered through frame 6 (complete) and one roll in frame 7.
Her highest-numbered frame with rolls = frame 7.

→ Scorer clears frame 7. All rolls for frame 7 are removed.
  Frame 6 is now the highest frame with rolls → it is now clearable.

→ Scorer clears frame 6.
  Frame 5 becomes clearable.

→ And so on back to frame 1.

UI for Clearing

A "Clear Frame" option should be accessible on the player's current frame — for example, a small trash/reset icon on the active frame cell, or a button in the pin input panel that appears when viewing a frame that is clearable. It should be visually distinct but not oversized — this is not a primary action.

No Confirmation Required
Clearing a single frame does not need a confirmation dialog — the player can immediately re-enter scores. The action is easily reversible by re-entering the rolls. Reserve confirmation dialogs for irreversible actions (i.e., marking the game complete).

08 Multiplayer & Sync

Access Model

Any person who knows the 6-digit code can access and edit the game. There is no concept of host, owner, or permission levels. All scorers are equal editors.

Sync Strategy — Polling

All connected devices poll the server for the latest game state on a fixed interval. Recommended interval: every 3–5 seconds. On each poll, the server returns the full current game state and the client re-renders. No websockets required.

  • Polling should pause or slow down when the app is in the background/screen is off.
  • There is no optimistic UI — the client waits for server confirmation before displaying a newly entered roll.
  • If two scorers submit a roll for the same player's same frame simultaneously, last-write-wins is acceptable. The small user base makes this collision extremely unlikely.

Offline / Error Handling

If a poll or submission fails, display a subtle connection status indicator (e.g. a small banner or icon). Do not block the UI. Retry automatically.

Sharing the Code

The game code is displayed prominently on the Setup screen (primary sharing moment) and remains visible on the Active Game screen for late joiners. Both screens include a one-tap copy button so scorers can easily paste the code into a text message.

Setup → Active

The creator taps "Start Game" on the Setup screen. At least one player must exist. Once started, the game moves to the Active state and scoring begins.

Active → Complete

The "Mark Complete" button becomes available only when all players have completed all 10 frames (i.e., all rolls for all frames are entered, no pending frames remain).

Tapping "Mark Complete" shows a confirmation dialog: "Are you sure? This will lock the game and it cannot be edited again." Two buttons: Confirm and Cancel. Any scorer with the code can trigger this.

Completed State

  • The full scorecard is shown in read-only mode — no pin input, no clear options.
  • The player(s) with the highest total score are highlighted as winner(s). Ties are possible and should be displayed as such (e.g. "Alice & Bob win").
  • The game code is still displayed (for others to view the result).
  • Completed games are stored indefinitely and accessible at any time via the code.

New Game Button

A "New Game" button is available on the Active Game screen. Tapping it shows a confirmation dialog: "Start a new game? This game will remain accessible via its code." Confirming navigates the user to the Home screen. The existing game is unaffected — it remains accessible to anyone with its code.

No Expiry
Games never expire or get deleted. The 6-digit code space (1,000,000 possible codes) is sufficient for the expected usage volume.

10 Data Model Reference

This is a logical description of the data — not a schema prescription. Adapt to your stack.

EntityFieldsNotes
Game code, status, created_at, completed_at Status: setup | active | complete
Player game_code, name, order_index Order index determines turn sequence and tiebreak
Roll game_code, player_id, frame (1–10), roll (1–3), pins Rolls are stored individually. Score is always computed from rolls, never stored directly.

Score Computation

Scores are always computed on the fly from the rolls — never stored. The scoring engine must:

  1. Walk frames 1–10 for a player in order.
  2. For each frame, determine if it is a strike, spare, or open.
  3. Look ahead to the next 1–2 rolls (from subsequent frames) to compute bonuses.
  4. If lookahead rolls are not yet recorded, mark that frame (and all subsequent) as pending.
  5. Return both per-frame scores and a running cumulative total.

Out of Scope
The following features are explicitly not included in this version: user accounts, player profiles, history across games, handicaps, animations, dark/light mode toggle, perfect game indicator, player randomizer, undo button, player name editing after game start.
